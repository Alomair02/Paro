## The chartEx acceptance contract (the hard-won finding)

A `cx:` part is **rejected by PowerPoint (silent repair, no useful error)** unless ALL
of the following are present, related, and typed. This was not guessable up front; it
was reverse-engineered by diffing against a known-good PowerPoint-emitted funnel.

A complete, openable chartEx funnel requires:
1. The `cx:` part itself (`ppt/charts/chartEx{N}.xml`), `cx:` namespace declared LOCALLY
   on the part root (never in the global NSMAP — golden-test discipline).
2. An **embedded workbook** + `cx:externalData r:id="..." cx:autoUpdate="0"` as the FIRST
   child of `cx:chartData`. Cache-only (no workbook) is REJECTED. `cx:autoUpdate` is a
   `cx:`-namespaced attribute — set via Clark notation, not a literal `"cx:autoUpdate"` key.
3. Content children PowerPoint expects: `cx:title`, `cx:dataLabels`/`cx:visibility` (in the
   series), and a `cx:axis` block (`cx:catScaling` + `cx:tickLabels`) AFTER `plotAreaRegion`
   inside `plotArea`. Element order is schema-enforced.
4. **Two sibling style parts** — `style{N}.xml` (chartStyle) and `colors{N}.xml`
   (chartColorStyle), related FROM the chartEx part. This was the last and least-obvious
   requirement; the part will not open without them. Rel types are the **2011** microsoft.com
   URIs (`.../office/2011/relationships/chartStyle` and `chartColorStyle`) — different year-path
   from the 2014 chartEx rel.

Three near-identical URIs that must NOT be conflated (each pinned in the registries):
- content namespace `cx:` → `.../office/drawing/2014/chartex`
- chartEx relationship → `.../office/2014/relationships/chartEx` (microsoft.com, NOT openxmlformats)
- content type → `application/vnd.ms-office.chartex+xml` (vnd.ms-office, NOT openxmlformats)
- style/color rels → `.../office/2011/relationships/chartStyle` / `chartColorStyle`

## What was built

- `builders/chartex_part_builder.py` — `ChartExBuilder` equivalents: local `cx:` namespace
  (`CHARTEX_NS`/`CHARTEX_NSMAP`/`cxqn`/`_cx`), `build_funnel_part_xml(workbook_rid)`,
  `emit_funnel(...)`, and `load_funnel_style_xml`/`load_funnel_colors_xml`.
- `builders/chartex_assets/funnel_style.xml`, `funnel_colors.xml` — canonical style/color
  templates, captured verbatim from a known-good PowerPoint funnel. **Theme-aware**: they use
  `schemeClr accent1..6` / `tx1`/`dk1`/`phClr` references, NOT hardcoded hex — so they pick up
  the deck's theme, they don't impose a foreign palette.
- `SlideState` (in `shape_emitters.py`) — separate `chartEx` index/path allocator
  (`next_chartex_path`, `_infer_next_chartex_index`), prefix-keyed on full `chartEx` so it
  never collides with the classic `chart` allocator.
- Registry constants: `ContentTypeRegistry.CHARTEX/CHART_STYLE/CHART_COLOR_STYLE`;
  `RelationshipRegistry.CHARTEX/CHART_STYLE/CHART_COLOR_STYLE` (+ whitelist entries).
- Slide dispatch: `_emit_shape` routes `type == "funnel"` to `emit_funnel`.
- All parts ride the existing single assembly path (`chart_parts` dict → `parts.update`).
  No second wiring path; orphaned-part trap avoided by construction.
- `tests/test_chartex.py` — property test (part exists, cache==workbook in `cx:` form,
  layoutId=funnel, the three required rels, content-types present, lumMod/lumOff ≤ 100000,
  global NSMAP stays cx-free).

## Edit Data — RESOLVED, NO FIX NEEDED

Engine-generated charts (classic AND chartEx funnel) are **fully editable in desktop
PowerPoint** — verified by opening an engine-built funnel on Windows desktop; right-click →
Edit Data works. Our workbook wiring (`package` rel → internal `.xlsx`, `externalData
r:id + cx:autoUpdate=0`) matches desktop-PowerPoint-emitted charts exactly.

Charts appear NON-editable in PowerPoint **Online** — this is an Online limitation (a
known-untrustworthy consumer, same as its upload banner), NOT an engine defect. **Do not
"fix" the workbook wiring based on Online behavior.** (Aside: openpyxl workbook ~4.9KB vs
PowerPoint's ~8.8KB — leaner, but accepted and editable; cosmetic.)

## Validation method note (carry forward to all chartEx work)

- LibreOffice renders chartEx blank/wrong even when XML is correct — NOT a trustworthy check.
- PowerPoint **Online** banners and disables editing regardless of validity — NOT trustworthy.
- **Desktop PowerPoint is the only gate.** Per-iteration check is structural (diff vs a
  known-good desktop-emitted sample). When PowerPoint repairs without a useful error, the
  fastest diagnosis is: diff against a known-good sample, OR let PowerPoint repair-and-save
  then diff its output (note: it may delete an unsalvageable part rather than fix it).

## Phase 1 notes (deferred by design — none are bugs)

1. **Data hardcoded in two places.** `build_funnel_part_xml` hardcodes the cache values;
   `emit_funnel` separately hardcodes the `series_list` feeding the workbook. They agree by
   coincidence today. The cache==workbook test guards drift, but resolver-driven data must
   unify both to ONE source. Also: no `type="funnel"` DSL branch yet — Phase 0 was proven via
   a direct `assemble_package` probe, bypassing parser/resolver on purpose.
2. **Title is a structural placeholder.** `cx:title` is emitted empty (PowerPoint shows
   "Chart Title"). Wire to `shape_data["title"]` (or omit) when resolver-driven.
3. **Inline styling path unexercised.** Per `CHARTEX_SPEC.md` §5, the native styling built for
   classic charts (`make_*` helpers + `ChartStyleRegistry`) extends to chartEx through inline
   `cx:spPr` on the series — the external style/color parts are just the required baseline, not
   a replacement. When wiring style/finish variation, put it in `cx:spPr` (consistent with
   classic charts), keeping the external parts as a fixed baseline.
